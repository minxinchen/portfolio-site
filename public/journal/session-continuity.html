AI 工作流 // 2026-05

同時用 Claude 和 Codex 踩坑記：怎麼避免淪為複製貼上搬運工

派 6 個 subagent 跑完第二輪評估那天，我直接喊停了——因為兩個模型開始拿對方的話當前提越疊越細，我反而變成在中間傳話的人。

Nio Chen 分類：AI 工作流 Repos：ai-workstation-handoff ↗ · context-recall-lab ↗

那次其實沒有任何檔案被改壞。真正失控的是「概念」：兩個 Agent 在互相回應的過程中，替一個還在實驗階段的資料夾憑空訂了升級門檻（n ≥ 50、通過率 ≥ 70%），還提前把它定性成正式記憶層。改錯程式碼可以 git revert，但整套前提被模型定死後，要花好幾倍力氣才拆得掉。

後來固定下來的三條習慣

  1. 先用 Codex 釐清需求，拍板後才交給 Claude 執行：Claude 的執行力很強，但給它一個模糊方向就會衝太快、順手把沒確認的邊界一起改掉。先跟 Codex 把範圍和停損點談清楚，我拍板後再讓 Claude 動手，返工少非常多。
  2. 來源一定要標清楚（超過 10 行的通常不是我打的）：整理對話紀錄時發現一個很準的切分——我親手打的指令幾乎都在 10 行以內、口語、偶爾還有錯字（像 dashbord）；超過 10 行工整的結構通常是貼進來的 Spec 或另一個 Agent 的整理。轉述時強制標註來源，日後回查才不會把 Agent 的建議誤認成我拍板的決定。
  3. 趕交付時，絕不同場改工具：有一次在同一個對話裡一邊寫正式文件、一邊順手修儀表板、建新 subagent、又跑存檔，結果當場爆出三個錯：儀表板字數標籤腦補寫 ~2,800（實測 3,213）、沒經確認直接把 v1 未審段落貼進新版、內文還混進工具自吹。之後嚴格切開：改工具另開新 Session，不跟交付搶同一個 Context Window。
