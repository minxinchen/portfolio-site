AI 工作流 // MULTI-AGENT GOVERNANCE

多 Agent 協作的踩坑紀錄：什麼時候該喊停，哪些決定不能交給 AI

很多人以為多 Agent 協作最難的是寫串接腳本，但我實際在個人工作站跑了幾個月後，發現真正容易失控的是「決策權被悄悄稀釋」與「同一個對話裡做太多雜事」。

剛開始同時用 Claude Code 和 Codex 協作管理自己的工作站時，我一度覺得「派 5、6 個 subagent 互相驗證」很有效率。直到有一次做到第二輪深度評估，我突然停下來喊卡——因為我發現，我從專案決策者，變成了在兩個 AI 之間複製貼上的訊息搬運工。

一、為什麼要「計劃性喊停」？檔案能救回，概念定性權不能

那次失控的徵兆非常微妙：兩個 Agent 沒有改壞任何程式碼，但它們開始互相拿對方的建議當成既定前提，越疊越細——替還沒成熟的實驗憑空設了升級門檻（例如「樣本數達 50、通過率 70%」），也提前把實驗身份框死成正式記憶層。

這件事讓我畫出一條很清楚的紅線：把「執行權」跟「定性權」分開。

  • 物理層（改檔、跑測試、整理報告）：可以交給 Agent 執行，改錯了還有 git revert 可以退回。
  • 概念層（這個實驗算什麼、邊界在哪、什麼時候升級）：必須留在人手裡。Agent 只能驗證事實、列候選選項，不能把未經拍板的假設直接寫成預設前提。

二、我後來固定下來的三角分工：釐清 → 拍板 → 執行

實際跑過幾十個 Session 後，我發現執行力特別強的模型（像是 Claude）有個很明顯的慣性：給它一個方向，它會衝得非常快，但有時會在早期邊界沒對齊的情況下直接改完整份檔案。

所以我後來把工作習慣拆成三步：先用 Codex 幫我釐清需求、抓盲點與設定停損點 → 我自己看過拍板 → 再把清楚的範圍交給 Claude 執行。

同時我也訂了一條來源溯源紀律：只要轉述另一個 Agent 的建議，就必須明標來源，不能無聲改寫成自己的結論。在整理對話紀錄時甚至出現過一個很有趣的辨識標準——「對話裡超過 10 行的工整規格通常不是我親手打的，我真實的決策信號都是 10 行以內的短句與反問。」分清這三層來源（人親打的短句、人採用的外部 Spec、平行 Agent 的建議），才不會在日後回溯決策時搞混誰才是拍板的人。

三、同一個 Session 邊趕交付、邊改工具，品質一定掉

另一個真實踩坑發生在趕一份技術文件時：我在同一個對話裡一邊改主文、一邊順手叫模型修儀表板顯示、加新的審稿 subagent、又順便存檔。結果模型在同一次對話裡連續出現三個失誤：

  1. 儀表板上的字數標籤直接腦補（寫 ~2,800，實測是 3,213）。
  2. 沒等我逐段確認，就把上一版沒審過的段落直接複製進新版。
  3. 主文裡開始混進「工具存在感」，而且出現「廠房有這套控制器，所以操作員不用重新學習」這種明顯的邏輯跳躍。

根因其實很簡單：Meta-task（改工具、設計新流程）跟 Product-task（完成交付物）都在搶同一個 Context Window 的注意力。自那之後我就立了一條鐵則：一個 Session 只做一條主軸，要做工具改造就另開新對話，絕不在趕交付時插隊改架構。

好的多 Agent 工作流，不是讓模型自己聊成一團，而是讓每一次交接都有檔案證據、每一個停損點都由人決定。
