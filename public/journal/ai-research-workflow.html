AI 工作流 // BLUEPRINT v1.0

單一 Prompt 排程壞掉之後：我怎麼重構 GitHub 技術雷達管線

收完六期自己排程的 GitHub 技術日報後，我直接把它暫停了——沒抓到 7 日快照的專案被混進排行、未實作的點子寫得像跑過實測，寄信失敗也沒有去重紀錄。這篇記錄拆成階段式管線後的 Blueprint。

Nio Chen 2026-11 狀態：設計藍圖（尚未全自動部署）

原本的做法是用單一排程 Prompt 每天早上九點直接產一封研究信，結果發現一個步驟沒抓到資料，後面整段分析就開始腦補。重構後把整條研究流程拆成「資料蒐集與查證」跟「評分與 Case Study 拆解」兩段，中間加上明確的檢查關卡：

STAGE 1 // DISCOVERY & VERIFY
發現候選 → 去重 → 核對來源與同窗口快照

從 GitHub Trending 與搜尋撈候選專案，排除歷史已推薦與疑似灌星項目；核對 README、commits、releases 與同起訖日期的 7 日 Star 變化。

STAGE 2 // SCORING & CASE STUDY
加權篩選 2–4 項 → 深入拆解一個 MVP 提案

僅對具備可比快照的專案計分（Star 速度 50% / 加速度 20% / 落地 15% / 適配 10% / 安全 5%），挑一個拆出問題、基準組、實驗組與失敗條件。

寄出前的三道檢查關卡

Gate 1｜Star 資料是否可比較？
  • 必須有同起訖日期的逐日快照才算 Δ7d 與日均增速。
  • 沒有相鄰同長度窗口就標「無法計算」，不拿總 Stars 替代。
  • 缺資料的專案只作質性介紹，不進數值排名。
Gate 2｜Case Study 是否寫清驗收條件？
  • 列出問題、基準組、實驗組、資料、指標與失敗條件。
  • 尚未實作的內容一律標為「設計構想」，優先選本機可跑的小型 MVP。
Gate 3｜寄送失敗怎麼處理？
  • 寄出前先查當日 Run Log，防止重複發信。
  • HTML 生成失敗保留草稿並標記失敗；只有收到郵件服務回傳的 Message ID，才更新為已寄送。

最小持久化檔案結構

先不上資料庫，用純檔案就能直接進 Git 追蹤每次執行、來源快照與失敗原因：

workflow/
  config.yaml             # 排程、主題、評分權重、收件設定
  runs/YYYY-MM-DD.json    # 當日狀態、錯誤與郵件 ID
  sources/                # Star 快照、README 來源與時間戳
  history/repos.json      # 已推薦專案清單，避免重複
  reports/YYYY-MM-DD.html # 寄送前的 HTML 產物
  evaluations/            # Quality Gate 審查紀錄

這份規格目前還停在 Blueprint 階段（六期郵件是用原本的 ChatGPT 定時任務跑出來的，目前已暫停）。下一步要等實際改寫成 Codex／本機腳本後，再把去重與重試測試補齊。
