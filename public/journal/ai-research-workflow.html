AI 工作流 // WORKFLOW BLUEPRINT v1.0

把每日技術追蹤拆成兩條管線：GitHub 雷達 × AIoT 微課的 Workflow 設計

如果把「追新開源專案」跟「每天學一個 AIoT 基礎觀念」塞進同一個大 Prompt 跑排程，很快就會遇到資料不可比、課程重複寄送、失敗卻回報成功等問題。這篇拆解我如何把它改畫成雙管線藍圖。

Nio Chen 2026-11 分類：AI 工作流

一開始我只是用每日定時任務寄給自己一封技術摘要信，連續收了六期之後，很快就看到單一 Prompt 排程的極限：有時候它會把沒抓到 7 日快照的專案混進排行，有時候會把「實驗構想」寫得像「已經跑完的實測」，遇到寄信失敗也沒有乾淨的重試與去重紀錄。

所以我先停掉排程，把整件事重構成一份可交給 Codex 或 Claude Code 實作的 Workflow Blueprint（v1.0）：核心想法是「分流處理、合流審查、失敗不偽造完成」。

一、雙管線架構：分流產出，合流審查

每天觸發時，Orchestrator 先產生當日 Run ID 並檢查是否已經寄出（防重複），接著同時啟動 A、B 兩條互不干擾的生產線，最後在 Quality Gate 合流：

PIPELINE A // GITHUB RADAR
1. 發現候選 → 2. 查證來源 → 3. 評分 → 4. 拆 Case Study

去除歷史已推薦與疑似灌星專案；核對 README、commits 與同窗口 7 日 Star 變化；以 Star 速度 50% / 加速度 20% / 落地 15% / 適配 10% / 維護安全 5% 篩出 2–4 項，最後深入拆解一個可驗收 MVP 提案。

PIPELINE B // AIoT MICRO-LESSON
1. 讀進度 → 2. 每日一課 → 3. 無硬體練習 → 4. 接回 Agent

依進度表（Day 1 概念一路到 Day 11 工業應用）選下一個未完成單元；限制 200–350 字、3–5 分鐘讀完；設計不需買硬體的模擬思考題，並明確區分「固定閾值規則」與「真正的 AI 推論」。

二、四道明確的 Quality Gate

很多 AI 自動化最容易出錯的地方不在生成，而在「沒有明確說什麼條件算不通過」。這份藍圖把審查拆成四道具體關卡：

  • Gate 1｜Star 資料是否可比較？ 必須有相同起訖日期的逐日快照才算 Δ7d 與日均增速；缺少相鄰同長度窗口就標「無法計算」，絕不拿總 Stars 替代，缺資料的專案只作質性介紹、不混入數值排名。
  • Gate 2｜Case Study 是否真的可驗收？ 每個提案都要寫清基準組、實驗組、輸入輸出與失敗條件；未實作的內容一律標記為「設計構想」，優先挑本機可跑的小型 MVP。
  • Gate 3｜AIoT 課程是否對齊初學者？ 每次只教一個新概念；不因為掛了「智慧」兩個字就把固定閾值自動化稱為 AI。
  • Gate 4｜寄送失敗如何處理？ 寄出前先查當日寄送紀錄防重複；HTML 失敗保留草稿並標記失敗；只有拿到郵件服務可靠回傳的 Message ID，才允許把當日狀態更新為已寄送。

三、最小持久化資料結構

為了讓每次執行都可追溯、跨日不失憶，藍圖先定義了最小檔案結構（刻意不先上資料庫，純 JSON / YAML / HTML 就能用 Git 追蹤）：

workflow/
  config.yaml             # 排程、主題、評分權重、收件設定
  runs/YYYY-MM-DD.json    # 每次執行狀態、錯誤與郵件 ID
  sources/                # Star 快照、README 來源與時間戳
  history/repos.json      # 已推薦專案清單，避免重複
  lessons/progress.json   # AIoT 已完成課程進度（目前至 Day 3）
  reports/YYYY-MM-DD.html # 寄送前的 HTML 電子報產物
  evaluations/            # Quality Gate 審查結果與失敗原因
現況與誠實邊界

這份文件是 Workflow Blueprint（設計規格），不是已經 24 小時全自動跑在伺服器上的程式。2026/10/30–11/04 期間確實產出並寄出了 6 期個人研究電子報（包含 AIoT Day 1–3），但定時排程目前已暫停，未來部署時會依這份規格逐項補齊自動化去重與重試測試。
