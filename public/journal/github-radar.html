開源雷達 // 2026-11

連追六期 GitHub AI 專案後，我怎麼決定「不安裝」

2026/10/30 到 11/04 跑了六期 GitHub AI 實作雷達。最後裝進工作站的工具沒幾個，但從 Superpowers、pstack、Ponytail 身上借走的設計思路，反而省了我最多時間。

Nio Chen 分類：開源雷達 狀態：實作選型紀錄

多裝一套自己沒摸透的 Agent 框架，通常只會換來多一層要修的設定檔。追完六期 GitHub 專案後，我發現自己最常做的決定其實是「看懂思路，但不裝整套工具」。

幾個值得拆開看的專案

專案 吸引我的設計點 我實際拿來怎麼用
Superpowers 把規劃、測試、驗證拆成可重複調用的 Skill，不靠臨場長 Prompt 碰運氣。 檢視哪些重複規範應該獨立成 Skill，避免主記憶檔越塞越大。
pstack 把 Prototype（先測資料拿不拿得到）和 Feature 實作、驗收明確拆開。 做 WP Search Lab 時直接讀原始規範適配到 Codex：先跑 CORS 原型，確認未開跨來源的網站會被瀏覽器擋，直接定調以 HTML 匯入為離線核心。
Ponytail 核心立場很直白：先問現有工具重用夠不夠，盡量減少不必要工程。 拿掉多餘框架，讓 WP Search Lab 直接打包成單檔離線 HTML，零建置即可打開。
Claude-Mem / Lightpanda 分別對應跨 Session 檢索與輕量瀏覽器執行環境。 列入觀察清單，重點看副作用：省 Token 後會不會抓到舊版本？跑更快之後擷取欄位會不會缺？

決定要不要動手試的四個檢查點

  1. 先核對依賴與授權：要整合進工具的套件，先看清楚 MIT、Apache-2.0、BSD-2-Clause。做 WP Search Lab 時就抓到 entities 的授權文字標錯，這種小錯第一輪沒修，後面很容易遺漏。
  2. 沒有同窗口快照，就不要比熱度：追蹤 7 日 Star 變化（Δ7d）一定要同起訖日期；缺資料就標「無法計算」，不拿總 Stars 硬排。
  3. 先定對照組再看效能宣稱：宣稱快幾倍或省多少 Token，若沒有固定同一批輸入、也沒確認輸出正確率沒掉，數字就沒有參考價值。
  4. 能借思路就不硬搬環境：像 pstack 原本針對 Cursor Agent 設計，在我當下的 Codex 環境沒有對應原生 Agent 類型，直接讀原規範並標明環境差異適配，比硬套外掛乾淨得多。
展開：這份觀察的證據範圍

pstack 規範適配，以及 parse5、@mozilla/readability、robots-parser 整合已經在 WP Search Lab 實測並納入 42 項自動化測試。Claude-Mem 與 Lightpanda 的對照目前仍停留在實驗設計階段，尚未跑完跨工具基準測試。
